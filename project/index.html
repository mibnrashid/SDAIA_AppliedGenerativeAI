What must be in it

Six requirements. All six are graded. "Working" means it runs on a laptop from a fresh clone — no deployment needed.

1

Your own documents

Ten to thirty pages you actually care about — a policy, a manual, a handbook, a set of regulations. Not a tutorial dataset. If real documents are hard to get, generated sample data is allowed — say so plainly in your README. Nothing confidential: we are on a free tier and Google may use free-tier inputs to improve their models.

Where it comes from — you.

2

A retrieval pipeline

Ingest, chunk, embed, store, and retrieve, with metadata carried through — source, page, section. Hybrid search — keyword and vector combined — because pure vector search misses exact identifiers, acronyms and names.

Where it comes from — Lab 2, cells 3–19.

3

Grounded answers with citations

Every fact traceable to a source and a page. And when the documents do not contain the answer, the assistant says so instead of inventing one. An assistant that always answers is worse than one that sometimes declines.

Where it comes from — Lab 2, cell 11.

4

At least two tools

Plain Python functions are fine — no MCP, no external service required. Each must do something retrieval cannot: compute something, look something up in structured data, filter, or check a live value. Retrieval itself does not count as one of the two — a tool that just searches your documents again is not a tool. Each one needs a clear purpose, defined inputs and outputs, and arguments validated before it runs.

Where it comes from — Lab 3, cells 2–5.

5

An agent loop

The model decides when to retrieve, when to call tool 1, when to call tool 2, and when to call both — rather than you hard-coding the order. Keep the step cap, and make sure a failing tool does not take the whole application down. Print the trace so you can show it on Thursday.

Where it comes from — Lab 3, cell 8.

6

Evidence that it works

A golden set of at least five questions you know the answers to, and a measured hit rate. Keep the test cases in the repository so the numbers can be re-run rather than taken on trust.

Where it comes from — Lab 2, cells 21–24.

What makes a project useful

The product should produce something a real user can act on: a sourced answer, a comparison, a checklist, a score, a report, a plan, a task file, or a safe draft action. Avoid building a generic chatbot with no clear user, data, workflow, or outcome. A focused solution that works well is stronger than a large unfinished system.

Bringing your own? Say it out loud on Monday and I will tell you whether it passes the two tests before you spend a day on it.

How to build it

There is no scaffold notebook this year. You are building a repository, because that is what goes in a portfolio — nobody hires anyone off a Colab link. The logic is code you have already run in the labs. The work is moving it out of notebooks and making it run on a laptop.

What to build it with

The left column is what the labs use and what I recommend. The right column is accepted. Marks are for a correct, useful, understandable implementation — not for picking an expensive tool.

ComponentRecommendedAlso accepted
Language Python Python stays the main language for product logic.
Interface A command-line app Streamlit or Gradio if you want a UI — worth it if you plan to deploy.
Model gemini-2.5-flash-lite Another hosted API, or an approved local model.
Embeddings gemini-embedding-001 A local sentence-transformers model, or another API.
Vector store Chroma Qdrant Cloud, Supabase pgvector, Pinecone, Weaviate, or another suitable store. Qdrant Cloud has a free prototype cluster; Supabase is useful if you also need Postgres tables or storage.
Retrieval Hybrid BM25 + vector Pure vector search meets the minimum, but it will miss exact identifiers and acronyms — which is why the labs do hybrid.
Deployment (optional) Streamlit Community Cloud HuggingFace Spaces or Render. Free-tier limits change — check them before the demo.

The repository blueprint

project-name/
├── app.py                          how a person talks to it
├── requirements.txt                pin your versions
├── README.md                       a stranger must succeed with this
├── .env.example                    GEMINI_API_KEY=your_key_here
├── .gitignore                      must contain .env and data/ if private
├── data/sample_documents/          your documents
├── scripts/ingest_documents.py     run once to build the index
├── src/config.py                   keys, model names, constants
├── src/schemas.py                  the shapes your code trusts
├── src/llm/client.py               the model call
├── src/llm/prompts.py              role, task, limits, output format
├── src/rag/loaders.py              read PDFs, text, CSV
├── src/rag/chunking.py             split into retrievable pieces
├── src/rag/embeddings.py           text → vectors
├── src/rag/vector_store.py         Chroma (or your choice)
├── src/rag/ingest.py               load → chunk → embed → store
├── src/rag/retriever.py            hybrid search
├── src/agent/orchestrator.py       the agent loop
├── src/agent/tool_registry.py      tool schemas the model can see
├── src/agent/guardrails.py         step cap, allow-list, timeouts
├── src/tools/tool_1.py             your first tool
├── src/tools/tool_2.py             your second tool
├── src/services/product_pipeline.py  wires it all together
└── evaluation/test_cases.json      golden set + the six scenarios

This structure is not mandatory. A smaller project may combine files; a bigger one may add modules. What matters is that I can find the prompt logic, the RAG pipeline, the agent, the tools, the app, and the test evidence without asking you where they are.

The six test cases to keep in the repository

Not a separate report — just enough evidence that someone can re-run your claims. Show: a normal request; a request where the evidence is missing; one using tool 1; one using tool 2; one where the agent correctly uses both; and one handled failure.

The one new thing

Outside Colab there is no Secrets panel. Your key goes in a .env file that is never committed, and python-dotenv loads it:

from dotenv import load_dotenv
import os
load_dotenv()
API_KEY = os.getenv("GEMINI_API_KEY")

Commit .env.example with the variable name and no value. Put .env in .gitignore on your first commit, not your last. A leaked key in git history is the most common way a portfolio repository embarrasses its author.

Optional: deploy it. +5 bonus, capped at 100.

A working published URL earns the bonus. Not required, and it earns nothing if the basics are missing — do it only once the six requirements are met.

  • Streamlit Community Cloud — wrap app.py in Streamlit calls, push, connect the repository. About thirty minutes. Free, deploys straight from GitHub, and handles secrets through the deployment settings.
  • HuggingFace Spaces — Gradio or Streamlit, same shape, and the link looks good in a portfolio.
  • Render — when you need a custom Python web service or a different architecture.

Whichever you pick: test the same Python version locally and in deployment, keep dependencies in requirements.txt, and store secrets outside the repository.

A note on Vercel: it runs Python as serverless functions, which means no persistent filesystem, so your Chroma index will not survive between requests. Making it work means moving to an external vector store such as Supabase pgvector. That is a genuine project in itself, not a deploy step — worth doing after the course, not during it.
