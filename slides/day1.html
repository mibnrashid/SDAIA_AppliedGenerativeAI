Part one

How the thing actually works

Forty minutes of mechanics. Everything after this depends on it.

We are going to spend the next forty minutes under the bonnet, and some of you will find the first ten minutes of it easy.

Stay with me anyway, because the vocabulary we set here is what I will use for the rest of the week without re-explaining it.

Two kinds of model

Discriminative

Draws a boundary. Given input, pick a label.

"Is this transaction fraud?" → yes / no

Fixed set of answers. You can measure accuracy directly.

Generative

Models the distribution. Given input, produce new content.

"Write the fraud alert for this customer." → a paragraph that never existed

Infinite possible answers. "Correct" is much harder to define.

That second column is why everything this week is about constraining the output.

The practical difference is not the architecture, it is what you can promise your users. A classifier has a fixed set of answers, so you can test it exhaustively.

A generative model can return anything, which is exactly why the rest of today is about narrowing what it is allowed to say.

That is one slide on theory. We are moving on.

Mechanics

A token is not a word

The model never sees letters or words. Text is cut into tokens — common chunks, learned from data — and each one becomes a number.

"Generative models are unbelievably useful."

Generative models are unbelievably useful.

6 words · 10 tokens. Common words are one token; rare ones get broken up.

You are billed per token, in and out. Tokens are the unit of everything: cost, limits, speed.

Look at "unbelievably". It is one word to you and four pieces to the model, because it is rare enough that the tokenizer never learned it whole.

The rule of thumb for English is about four characters per token, so a hundred words is roughly a hundred and thirty tokens.

Hold on to that number, because in two slides it is going to be very different for Arabic.

Mechanics · live

The same sentence costs more in Arabic

English

"The National Data Governance policy applies to every entity."

≈ 11 tokens

Arabic — the same meaning

تنطبق سياسة حوكمة البيانات الوطنية على كل جهة.

≈ 26 tokens

0 tokens · 0 characters

Approximate. A heuristic, not the real tokenizer: ~4 characters per token for Latin script, ~2 for Arabic.

Two to three times the tokens for the same sentence. That is not a rounding error, it is your budget, and nobody warns you about it.

Type something of your own into the box on the right and watch the count. Then paste the Arabic translation of it underneath and watch it jump.

This comes back on Wednesday when we price an internal assistant, and the Arabic version of the same product costs noticeably more to run.

Mechanics

The context window

Everything the model can see at once: your system instruction, the conversation so far, any documents you pasted in, and the answer it is writing.

Measured in tokens. Go over it and the call fails, or the earliest content silently falls out.

The consequences

  • You cannot paste a 400-page policy manual into a prompt.
  • A long chat quietly forgets its own beginning.
  • Bigger windows are real, but you pay for every token you fill.

This is why chunking exists tomorrow.

The window is not memory. Nothing is remembered between calls — every request re-sends the entire conversation, which is why long chats get expensive.

Say the last line slowly, because tomorrow morning somebody will ask why we bother cutting documents up, and this slide is the answer.

Mechanics

It is predicting the next token. That is the whole trick.

"The capital of Saudi Arabia is"

Riyadh — 94%the — 2%located — 1%a — 0.4%

It picks one, appends it, and asks the same question again. Hundreds of times.

Nothing in that loop checks whether the sentence is true. It checks whether it is likely.

Fluent and wrong are not opposites here. Fluency is the objective; truth never was.

This is the single most useful thing to understand about these models, and it explains almost every failure you will hit this week.

There is no lookup, no database, no fact check in that loop. It is picking a likely next piece of text, over and over.

When you understand that, hallucination stops being surprising and starts being something you design around.

The dial you actually turn

Temperature

Same prompt three times: "Write one line describing a data governance policy."

temperature = 0.0

"A data governance policy defines how data is managed."

Run it three times, get this three times. Predictable.

temperature = 0.7

"A data governance policy sets the rules for how an organisation handles its data."

Varied wording, same substance.

temperature = 1.2

"Think of governance as the traffic law of your data highways — signs, lanes, and fines."

Creative. Also where it starts inventing.

Extraction, classification, anything you parse: 0.0 to 0.2. Drafting and ideation: 0.7 up.

Temperature reshapes the probability list before it samples. Near zero it always takes the most likely token, which is why the output repeats exactly.

The mistake I see constantly is people running extraction tasks at the default temperature and then complaining that the output is inconsistent.

In the lab you will run the same prompt three times at zero and three times at one point two, and see this for yourself.

Mechanics

Hallucination is a property, not a bug

The model produces likely text. When it has no grounding, likely text still arrives — confident, well formatted, and wrong.

It will invent a policy number, a citation, an article, a date. Fluently.

You design around it

  • Ground it — give it the document. That is tomorrow.
  • Cite it — make it show which chunk it used.
  • Type it — a schema removes room to waffle. That is this afternoon.
  • Check it — validate in code before you act.

There is no patch coming. Every mitigation on this slide is architecture, not a setting.

I want to be honest with you here: this is not a defect that gets fixed in the next model release. It is what next-token prediction does when it lacks grounding.

So we do not try to stop it. We build systems where a made-up answer is caught, or cannot be acted on, or is visibly unsupported by a citation.

Every one of those four bullets is a day of this course.

Part two

Make it reliable

Same model, better instructions. This is the cheapest win you will ever get.

Everything so far has been how the model works. From here it is what you do about it.

And we start with prompting, because it costs nothing and it is where most of the improvement actually lives.

Roles

System instruction vs user message

System

Who the model is, what it may do, how it answers. Set by you, the developer. Sent on every call.

"You are an HR policy assistant. Answer only from the provided documents. If the answer is not there, say so."

User

The question. Comes from outside — possibly from someone who does not wish you well.

"How many annual leave days do I get?"

That separation is a security boundary — and on Thursday you will spend the morning attacking it.

Everything on the left is your policy. Everything on the right is untrusted input, in exactly the way a web form is untrusted input.

The uncomfortable part, and we will prove it on Thursday, is that both of these end up as text in the same window, so the boundary is a convention rather than a wall.

Remember this slide. I will put it back up on day five before we break it.

Prompting

Anatomy of a prompt that holds

RoleWho is answering, and what they are responsible for.
ContextThe documents, the data, the conversation so far — clearly delimited.
TaskOne instruction, in the imperative. Not three questions in a paragraph.
FormatExactly what shape the answer takes. JSON, a table, three bullets, under 50 words.
ExamplesOne or two done correctly. Worth more than another paragraph of instruction.

Delimit your context: <document> … </document>. Vague prompts fail in ways you cannot debug.

When a prompt misbehaves, walk these five and find the missing one. Nine times out of ten it is format, and the tenth time it is that you asked three things at once.

The delimiters matter more than they look. They tell the model where your instructions end and untrusted content begins, which is also a first line of defence on Thursday.

Prompting

Show it, don't tell it

Before — zero-shot

"Classify this support ticket."

→ "This appears to be a complaint about slow service, possibly urgent."

A different shape every time. Unparseable.

After — two examples

"Ticket: 'Portal is down.' → outage | high
Ticket: 'How do I reset my password?' → account | low
Ticket: '…' →"

→ "billing | medium"

Same shape every time. Now you can split on the pipe.

Two examples usually beat two paragraphs of instruction. Cheaper, too.

Examples do something instructions cannot: they demonstrate the output shape, the level of detail and the vocabulary all at once.

Two or three is normally enough. If you find yourself at ten examples, that is the signal that the task might genuinely need fine-tuning.

And notice what the right-hand column bought us — output we can parse, which is exactly where we are going after the break.

Part three · the ceiling

Make it typed

The difference between a chatbot and a component in a system.

This last half hour is the part of today that earns the word "applied", and it is missing from almost every generative AI course I have seen.

Everything up to now made the model behave better. What follows makes its output something software can depend on.

The ceiling

Free text is unusable inside software

You ask for the customer's name and how urgent the request is. You get:

"The customer is Sara Al-Otaibi and this seems quite urgent."

"Name: Sara Al-Otaibi
Urgency: High"

"Sure! Here's what I found — the sender appears to be Sara…"

Three runs, three shapes. Now write the if statement that routes the urgent ones.

Regex over model output is a bug you have not hit yet. The fix is not a better parser — it is a contract.

Everybody in this room who has tried to build on top of a model has written a fragile parser like this, and watched it break in production on a Thursday.

The instinct is to write a smarter regex. That is the wrong move — you are patching a symptom of an unconstrained interface.

What we want is a contract the model has to satisfy before the response even reaches our code.

The ceiling · code

Ask for JSON, and define the shape

from google import genai
from google.genai import types

client = genai.Client(api_key=API_KEY)

schema = {
    "type": "object",
    "properties": {
        "name":    {"type": "string"},
        "intent":  {"type": "string",
                     "enum": ["question", "complaint", "request"]},
        "urgency": {"type": "string",
                     "enum": ["low", "medium", "high"]},
    },
    "required": ["name", "intent", "urgency"],
}

resp = client.models.generate_content(
    model="gemini-2.5-flash-lite",
    contents=message,
    config=types.GenerateContentConfig(
        response_mime_type="application/json",
        response_schema=schema,
        temperature=0,
    ),
)

Argument by argument

  • enum — the model cannot return "quite urgent". Only these three strings.
  • required — these keys will be present.
  • response_mime_type — no prose, no markdown fence.
  • response_schema — the contract itself.
  • temperature=0 — extraction, so no creativity wanted.

Walk it top to bottom. The schema is ordinary JSON Schema — the same thing you would write for an API, which is the point.

The two highlighted lines are what actually change the behaviour: one says the response must be JSON, the other says which JSON.

Look at the enum on urgency. That single line is the difference between branching on three known values and parsing English adjectives forever.

The SDK also accepts a Pydantic model in place of that dict, which is what I would use in a real project.

Why this matters

No regex. No string matching. No "if the answer contains the word urgent".

The model is now a function that returns a typed value, and the rest of your system does not need to know an LLM was involved.

Everything on Tuesday — tools, agents — is this idea again, in a loop.

Stop here for a second, because this is the slide the whole day was built towards.

That if-statement is ordinary Python. It does not know or care that a language model produced the dictionary it is branching on.

When you can do this, generative AI stops being a chat window and becomes a component you can put inside a system, with everything that follows — testing, monitoring, and being on call for it.

The ceiling · code

Wrap it once, use it all week

import json, time

MODEL = "gemini-2.5-flash-lite"

def ask(prompt, system=None, temperature=0.2,
        schema=None, tries=3):
    # Build config; only ask for JSON if a schema was given.
    opts = {"system_instruction": system,
            "temperature": temperature}
    if schema:
        opts["response_mime_type"] = "application/json"
        opts["response_schema"] = schema
    cfg = types.GenerateContentConfig(**opts)

    for n in range(tries):
        try:
            r = client.models.generate_content(
                model=MODEL, contents=prompt, config=cfg)
            return json.loads(r.text) if schema else r.text
        except Exception:
            if n == tries - 1: raise
            time.sleep(2 ** n)   # 1s, 2s, 4s

What it buys you

  • One place to change the model name.
  • Retries with backoff — you will hit rate limits tomorrow.
  • Schema optional: prose when you want prose, typed data when you don't.

Given complete in the notebook. Read it, don't retype it.

You are given this one complete, because the lesson is in reading it, not in typing it.

Catching bare Exception is deliberately blunt for teaching; on Wednesday we replace it with a proper retry decorator that only retries the errors worth retrying.

The sleep line doubles each attempt — one second, two, four. That is exponential backoff, and it is what keeps you from making a rate limit worse.
